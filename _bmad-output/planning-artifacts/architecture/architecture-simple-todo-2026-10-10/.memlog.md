updated: 2026-10-13T12:17

- (decision) Maintain a separate React frontend and Spring Boot backend so task and diary flows remain local to one user without introducing auth, tenancy, or shared-workspace complexity.
- (decision) Bind the app to a layered architecture: UI -> REST API -> application/domain services -> persistence, with the database and external config as the only cross-layer concerns.
- (decision) Fix task status to exactly TODO, in progress, and completed; task recency is the governing field for the seven-item dashboard and history selection.
- (decision) Use browser/device local calendar dates as the identity for Diary entries, with one entry per date and a read-only lock after that date passes.
- (decision) Keep diary content user-authored and immutable in the app; no AI generation, rewriting, or summaries are part of the product contract.
- (decision) Use PostgreSQL with Spring Data JPA and environment-based configuration; API URL and CORS must not be hardcoded for local development.
- (decision) Keep the product scope to single-user personal workflows and defer multi-user auth, collaboration, device sync, and AI features.
- (version) Frontend: React + Vite; Backend: Spring Boot 4.0.7; Java runtime: Java 25; Persistence: PostgreSQL; Build: Gradle compatible with the selected Boot and Java versions.
- (event) Architecture spine drafted from PRD and UX constraints
- (decision) V1 runs locally on the user's machine: React UI, Spring Boot API, and PostgreSQL database are reachable only through localhost development endpoints. Do not expose the unauthenticated app/API to an untrusted network. Authentication and authorization remain deferred until after the local personal-use trial; add them before any network exposure.
- (version) Verified current greenfield baseline selected by user: React 19.3.0; Vite 8.3.4; Node 22.12+ per Vite engine; Java 25 LTS; Spring Boot 4.1.1; Gradle 9.8.1; Spring Data JPA aligned to Boot; PostgreSQL 18.6. Sources checked 2026-10-10: react.dev/versions, npm registry latest metadata for vite, OpenJDK JDK 25 project page, Spring Boot system requirements, Gradle compatibility matrix, PostgreSQL versioning policy. Spring Boot 4.1.1 supports Java 17-26 and Gradle 8.14+/9.x; Gradle 9.1+ runs on Java 25.
- (decision) CORS is explicit and environment-configured; local development allows only the configured localhost frontend origin, not a wildcard. API base URL and PostgreSQL credentials come from environment configuration; frontend accesses data only through the REST API and backend owns validation, domain rules, and persistence.
- (version) User already has Node.js 26.7.0 installed and approved using it locally. Vite 8.3.4 declares Node engine ^20.19.0 || >=22.12.0, so Node 26.7.0 is compatible. Node 26 is Current, not LTS, per official Node release schedule; retain for local development and reassess before production deployment. Java 25 is already installed and is within Spring Boot 4.1.1's documented Java 17-26 compatibility range.
- (constraint) The UX contract fixes the frontend as one single-page Tasks-then-Diary experience; Task History is a dialog over that page, not a separate route. Task deletion is available only from the dashboard; a failed delete keeps the task visible and is reported as failure.
- (constraint) The API contract requires a valid IANA X-Client-Time-Zone header for diary writes and history; missing or invalid values return 400 INVALID_TIME_ZONE. DiaryEntryType is exactly FULL_ENTRY or SUMMARY. One entry exists per local date and same-day saves upsert it.
- (decision) The user selected the verified current stack after comparing the PRD addendum's provisional Spring Boot 4.0.7 baseline. The addendum will be updated to match React 19.3.0, Vite 8.3.4, Node 26.7.0 for local dev, Java 25, Spring Boot 4.1.1, Gradle 9.8.1, Spring Data JPA managed by Boot, and PostgreSQL 18.6.
- (decision) Local runtime contract: bind React/Vite to 127.0.0.1:5173, Spring Boot to 127.0.0.1:8080, and PostgreSQL to 127.0.0.1:5432 by default; allow explicit port overrides through environment configuration, but never bind to 0.0.0.0 or wildcard origins. Set CORS to the exact configured frontend origin. Startup order is PostgreSQL service, database creation, API readiness/migrations, then frontend.
- (decision) Use Flyway versioned SQL migrations as the sole database schema evolution path, with the PostgreSQL Flyway module and Spring Boot-managed versions. The local PostgreSQL service/database must be available before API startup; Spring Boot applies migrations and becomes ready only after success.
- (version) Local installation verified: Node.js 26.7.0; Amazon Corretto OpenJDK 25.0.2.10.1 (LTS); PostgreSQL Windows service postgresql-x64-18 running at PostgreSQL 18.3. Selected target baseline remains PostgreSQL 18.6 (current supported minor); update local 18.3 to 18.6 before implementation, no upgrade performed.
- (decision) V1 uses last-committed-write-wins for task and diary mutations; there are no entity versions or ETag preconditions. After a successful mutation and whenever a tab becomes active, the client refreshes from the API; the backend's committed state is authoritative.
- (constraint) Client task/diary state is ephemeral presentation state only; no persisted browser cache or offline mode. Unsaved form text may remain in the active view for retry, but only API-confirmed results are represented as saved.
- (constraint) Before every diary API request, resolve the browser's current IANA timezone. Recheck date and timezone on page focus/visibility and at local midnight; when either changes, refresh diary eligibility and history before presenting them as current.
